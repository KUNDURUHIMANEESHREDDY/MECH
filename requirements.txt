# Scientific Computing
#
# NUMPY AND PANDAS UPPER BOUNDS ARE ALSO LOAD-BEARING, for the same reason as the
# ML pins below: transformer-lens 2.18 declares `numpy>=1.24,<2` and
# `pandas>=1.1.5,<2.1` on Python 3.11. With unbounded ">=1.24.0" and ">=2.0.0",
# a clean install resolved to numpy 2.4.6 and pandas 3.0.6, and the ML stack broke
# with a binary-ABI error that surfaces far from its cause:
#
#   ValueError: numpy.dtype size changed, may indicate binary incompatibility.
#               Expected 96 from C header, got 88 from PyObject
#
# raised on `import pandas` / `import sklearn` / `import transformer_lens` while
# `import numpy` alone still worked -- which makes it look like a broken install
# rather than a version-pinning problem. Six tests failed this way on a machine
# that had been fine an hour earlier.
#
# The trigger was unrelated to this project: installing OCR tooling for coursework
# pulled numpy up to 2.4.6. Because the bounds were missing, pip had no reason to
# hold transformer-lens back.
numpy>=1.24.0,<2
scipy>=1.10.0
matplotlib>=3.7.0
seaborn>=0.12.0
pandas>=2.0.0,<2.1

# Datasets / Parquet
#
# The pyarrow bound is load-bearing for the numpy<2 pin above, not for
# pyarrow itself. `datasets` is pulled in transitively by transformer-lens and
# imports pyarrow, which in 26.0.0 refuses to load against numpy 1.x --
# python/pyarrow/lib.pyx raises at import, and the traceback is nowhere near
# the cause:
#
#   ImportError: pyarrow requires NumPy 2.0 or newer, found 1.26.4
#
# 25.0.1 is the last release without that check (verified in the 26.0.0 and
# 25.0.1 tags of python/pyarrow/lib.pyx), and `import datasets` works against
# it: datasets 5.0.1, pyarrow 25.0.1, numpy 1.26.4.
#
# The alternative -- letting numpy float up to 2.x -- is not on the table:
# transformer-lens 2.18 declares `numpy>=1.24,<2`, and the pin above explains
# why that bound has to hold.
pyarrow>=15.0.0,<26.0.0

# ML / Interpretability
#
# The original transformers 4.57.6 stack is no longer acceptable: the strict
# October 2026 dependency audit reports known advisories for that release. Use
# the patched Transformers 5.x line and a TransformerLens 3.x release that both
# supports Transformers 5 and still exports the legacy HookedTransformer API.
# TransformerLens 4.0 removed HookedTransformer in favor of TransformerBridge;
# this upper bound is therefore intentional while API migration remains separate.
#
# TransformerLens 3.9 declares transformers>=5.9.0 and retains HookedTransformer.
# Transformers 5.20.2 is beyond the fixes reported by the current audit; its
# metadata requires huggingface-hub>=1.31.0,<3.0. Keep these ranges together so
# the resolver cannot recreate the known incompatible 2.x / transformers-5 or
# 4.x / HookedTransformer combinations.
#
# The numpy, pandas, and pyarrow upper bounds remain load-bearing for the
# project's scientific stack and its NumPy/PyArrow binary ABI.
torch>=2.6
transformers>=5.20.2,<6.0
transformer-lens>=3.9.0,<4.0
huggingface-hub>=1.31.0,<3.0

# Security tooling audits the installed Python environment, including the
# runner's preinstalled setuptools. Require a release fixed for PYSEC-2026-3447.
setuptools>=83.0.0

# MCP control plane (external agents drive MECH through tools, not the UI).
# Verified with 1.30.0; the FastMCP surface used here (tool/streamable_http_app
# /run_stdio_async) is stable across 1.x.
#
# The upper bound is load-bearing. mcp 2.x renamed FastMCP to MCPServer and
# changed the server API, so `backend/mcp_server/server.py` -- which does
# `from mcp.server.fastmcp import FastMCP` -- cannot import it at all:
#
#   ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x.
#   ... or pin 'mcp<2' to keep running v1 code.
#
# The mount failure is caught and logged rather than raised, so it fails no test
# and breaks no import: the control plane is simply absent, which is the worst
# way for a capability to go missing.
mcp>=1.30.0,<2.0.0
